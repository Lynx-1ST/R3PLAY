# Audio cache streaming proposal for v2.9

Status: implemented for dev-2.9.2r1. The original proposal below is retained as design context.

## Implemented contract and operating limits

The renderer submits `CacheAudio` through the allowlisted Electron bridge. Main validates
the sender/main frame with `trustedListener` and accepts only `{ id, url, bitrate?, level? }`.
It returns a small receipt immediately (`queued`, `deduplicated`, `busy`, `invalid`, or
`stopped`); no audio bytes cross IPC. The player never waits for background completion.
Standalone web/server caching remains unchanged; the legacy desktop multipart route is
retained for compatibility but the renderer no longer calls it or falls back to it.

`AudioCacheJobs` runs at most two jobs, with at most 32 active/queued variants. The key
includes track ID, backend-derived source, requested quality and bitrate hint; the
persistent key additionally records actual codec, bitrate, sample rate and bit depth.
Limits: 512 MiB/file, five minutes/active job, 15 seconds for headers, 20 seconds idle,
and five redirects. Failures are logged with track ID and reason, never signed URLs.

Privileged requests allow only the source CDN suffixes in `audioDownloadPolicy.ts`.
The broad browser policy `qq.com` is deliberately excluded. HTTP and HTTPS default ports
are supported for legacy providers; credentials, nondefault ports, cross-source redirects
and HTTPS downgrades are rejected. Every hop resolves DNS, rejects private/special-purpose
answers (including mixed DNS results), then pins an approved IP in a fresh socket while
keeping the original TLS hostname. Renderer headers/cookies and ambient proxy agents
are never used. Bilibili Referer is generated by the existing backend source policy.
If a source requires an unsupported CDN or proxy, caching fails without affecting playback.

`pipeline()` streams into an exclusive temp file and hashes SHA-256 incrementally.
Content-Length, actual bytes and HTTP completion must agree. A 206 is accepted only
when Content-Range proves the entire file. The file is synced, identified using a
64-byte signature and given a codec extension before `parseFile({ skipCovers: true })`;
this avoids runtime MIME-loader differences and buffering embedded artwork.

Each new final filename is unique, renamed on the same filesystem before a single
AudioVariant upsert. Previous cache stays referenced until the new row commits. DB/rename
failures remove only the new unreferenced file. Windows read locks can defer deleting
the old file; startup recovery removes unreferenced streaming files and abandoned temps.
Recovery starts after acquiring Electron's single-instance lock. Clearing cache cancels
and drains background jobs before clearing rows. App shutdown cancels jobs; restart
recovery covers files left by forced termination.

AudioVariant adds an idempotent `hash` column; migrated legacy rows default to an empty
hash. Inserts name columns so old upload writers and repeated startup remain compatible.
Lossless/Hi-Res/effects retain distinct keys. Requested quality that cannot be established
is rejected, not silently downgraded; Hi-Res also requires >48 kHz or >16-bit metadata.
Playback reuses `resolveCacheAudioPath` and `streamCachedAudio`, including Range and HEAD.

## Verification and rollout

Integration tests use a local HTTP fixture and real SQLite for concurrency/deduplication,
slow/truncated/oversized downloads, full versus partial 206, failed/expired source URLs,
redirect limits, metadata errors, cancellation/deadlines, rename/DB failures, restart
cleanup, variant separation and cached Range/HEAD responses. Network-policy tests prove
private/mixed DNS rejection, pinned lookup, Bilibili headers and header/idle timeouts.
Player tests prove playback/seek continue with a pending or rejected cache promise.
The Windows release pipeline also runs a bundled streaming probe under packaged Electron.

Reproduce memory comparison with:

```powershell
node --expose-gc --import tsx packages/desktop/scripts/benchmarkAudioStreaming.ts
```

On Windows, Node v24.21.0, a synthetic 128 MiB payload with FLAC 96 kHz/24-bit STREAMINFO
in separate fresh processes showed incremental peak RSS of 519 MiB for simulated
ArrayBuffer/Blob/main-buffer copies versus 58 MiB for disk streaming and metadata.
This is a synthetic buffering benchmark, not decoded audio playback or a production
memory guarantee. Real provider URLs can expire or reject direct backend requests;
those failures deliberately remain cache-only failures.

Rollout is dev-only. Back up the profile before upgrading. When returning to stable
v2.9.1, restore that backup, or stop the app and drop only the AudioVariant cache table
with SQLite (`DROP TABLE AudioVariant`). Stable will recreate it from the legacy Audio
rows. Stable's positional inserts and filename allowlist do not understand the new hash
column/streaming filenames; account, playlist and settings tables must be retained.
Do not enable automatic full-buffer fallback, which would reintroduce the memory issue.

## Initial proposal

The renderer downloads the entire remote response in `packages/web/api/r3play.ts`,
wraps it in a Blob/FormData upload, and the desktop Fastify audio route calls
`data.toBuffer()` before `cache.setAudio()` parses metadata and writes the file.
These steps can retain several copies of a Lossless/Hi-Res track in memory. Playback
already starts independently, and cache failures are caught in `player._cacheAudio()`.

Moving the download crosses a new trust boundary: a privileged backend would fetch
URLs supplied by the renderer. It also needs to reproduce source-specific request
headers and handle expiring URLs, redirects, partial responses, concurrent writes,
and existing quality variants. Changing all these paths during the stability pass
would risk playback and cache correctness. Keep the current behavior for v2.8.x and
implement the following as a separately tested v2.9 change.

1. Send a cache request containing the track ID, resolved URL and quality metadata
   through a trusted renderer IPC handler or the protected local backend. Validate
   a positive safe integer ID and explicit quality/source values. Treat reported
   quality as a hint; preserve actual format, bitrate, sample rate and bit depth.
2. Start a bounded background job. Deduplicate jobs for the same variant; limit
   concurrency, bytes, duration and redirects. Playback never awaits the job.
   Validate each redirect against the source's approved CDN hosts, reject private
   and loopback destinations, and generate source headers in the backend. Use the
   existing CDN policy as an input, but audit it for privileged fetching/SSRF.
3. Stream the full response to a unique temporary file inside `audio_cache` using
   `pipeline()` and calculate SHA-256 incrementally. Reject incomplete 206 responses
   and truncated downloads; never turn a partial song into a playable cache entry.
4. Read metadata from disk with `music-metadata.parseFile()` instead of rebuilding
   an ArrayBuffer/Buffer. Use `getCacheLevel()` with actual codec/bitrate and preserve
   source, format, sample rate and bit depth. Keep Lossless/Hi-Res and effects variants
   separate; never overwrite a higher-quality entry with an inferred lower quality.
5. Atomically rename on the same filesystem and then upsert the existing
   `AudioVariant` key. Handle Windows destination collisions and concurrent jobs.
   Keep the previous entry until the new file and DB row are durable. On a DB
   failure, remove only newly created, unreferenced files; clean abandoned temp
   files after cancellation or crashes.
6. Reuse `resolveCacheAudioPath()` and `streamCachedAudio()` for playback. Preserve
   full, byte-range, suffix-range and HEAD responses, metadata and variant selection.

Before rollout, test slow/truncated/oversized responses, redirects and private-host
rejection, expired source URLs, source headers, cancellation, concurrent jobs,
Windows rename behavior, metadata failures, DB failures and restart recovery.
Compare peak memory on large FLAC fixtures, and verify playback and seeking continue
when every cache failure path is exercised. Keep the old upload path available
until this replacement has equivalent integration and packaged playback coverage.
