# 2.9.7 stable verification

## Scope

Fix the release audit's playback validation, signed-URL mutation, standalone migration and WebM cache findings. Add on-demand per-process RAM diagnostics. Publish the stable installer only through the existing Windows release workflow.

## Artifact investigation

The published 2.9.6 installer is 159,423,913 bytes; locally built dev.4 is 130,547,946 bytes. Archive inspection shows 527,386,315 vs 445,835,383 uncompressed bytes. The main difference is duplicate `app.asar`/`app.asar.unpacked` production dependency trees: 80,622,897 vs 722,193 bytes of `node_modules` represented in the ASAR header. The independent `resources/runtime` inventories each contain 4,840 entries with identical sizes and no missing entries. This establishes a packaging-layout difference, not evidence of a measured runtime RAM reduction. Local hoisted dependencies differ from CI's pnpm workspace layout.

Dev.4 was uploaded locally and has no release-workflow provenance. Stable 2.9.7 must be built from a clean Windows Actions checkout and ship its provenance with the installer.

## Verification

- Regression tests first reproduced invalid ID acceptance, signed URL mutation, wrong migration selection and WebM cache failure.
- Real Chromium-generated WebM/Opus fixture checks signature detection, metadata parsing, persisted source/container, identical bytes and HTTP Range/MIME replay.
- Recovery removes orphan WebM files while keeping referenced ones.
- Migration tests cover ordered pending versions, repeated startup, rollback and downgrade watermark protection using SQLite.
- Diagnostics tests cover multiple renderers, all process groups, PID and optional Windows private memory.
- Real Chromium UI verification: RAM groups, PID/private-memory table, clear logs and 768/1024/1440 px screenshots pass.
- Full local suites: 677 desktop tests and 157 renderer tests; desktop, renderer and standalone server typechecks pass.

## Rollback

If a release regression is reported, retain user data and use the previous stable 2.9.6 installer while preparing a forward fix. Do not assume the updater automatically downgrades. Standalone migration failures leave both schema and version watermark unchanged.

## Metric semantics

Diagnostics takes one `app.getAppMetrics()` snapshot when opened/refreshed/exported; no new background polling. Values are KiB converted to MiB. Working sets include shared pages; their sum is not deduplicated physical memory. Private committed memory is shown when Electron supplies it. See [Electron ProcessMetric](https://www.electronjs.org/docs/latest/api/structures/process-metric) and [MemoryInfo](https://www.electronjs.org/docs/latest/api/structures/memory-info).

## CI configuration correction

The first stable workflow passed startup checks but a post-download native IPC check reported Last.fm `configured: false`. Turbo strict environment mode had removed Last.fm keys before desktop compilation. Release builds now explicitly pass the build environment (also allowlisted for future normal builds) and fail before packaging if either Last.fm credential is absent from the compiled main bundle. The existing stable tag is rebuilt through the repository's explicit stable-rebuild workflow; the source tag is preserved and provenance separately records the workflow revision.

The standard rebuild produced and uploaded a verified Actions artifact after all build/configuration/runtime gates passed. Existing-release publication rejected a tag/target update by the default GitHub integration. The publisher now uploads checked artifacts and updates metadata without resending tag or target fields for an existing release. A recovery workflow only accepts artifacts from standard completed Windows workflows whose build, Last.fm configuration, packaged smoke tests and provenance gates passed. A publisher regression test rejects altered asset bytes and asserts that existing-release updates do not mutate Git references.
